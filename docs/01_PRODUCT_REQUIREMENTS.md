# SwasthAI: Product Requirements Document (PRD)

**Document Version:** 1.1.0  
**Classification:** Engineering Specification  
**Status:** Approved for Implementation Planning (Revised Single Generative Model Architecture)  

---

## 1. Overview & Scope Definition

This document establishes the functional, non-functional, and operational requirements for **SwasthAI**. All requirements are tagged with unique identifiers and strict priority levels:
* **P0 (Essential MVP):** Must be fully realized and verified on the target device for hackathon demonstration.
* **P1 (High-Value Expansion):** Secondary features that enhance clinical utility and engagement, scheduled immediately after P0 stability.
* **P2 (Advanced / Future Roadmap):** Extended capabilities intended for subsequent post-hackathon release cycles.
* **Research Gate (RG):** Requires explicit technical feasibility validation on the physical Snapdragon 8 Elite hardware prior to code integration.

* **US-08 (Reminders & Care):** *As a user, I want to set localized medication and follow-up consultation reminders based on my doctor's prescription.* (P1)

## 3. Functional Requirements (FR)

### 3.1 Local AI Chat & Conversational Experience (FR-CHAT)
* **FR-CHAT-01 (P0): Single Generative Model Dialogue:** The system shall execute conversational dialogue utilizing a single on-device generative model (**MedGemma 1.5 4B IT**) without external network transmission.
* **FR-CHAT-01A (P0): Multi-Turn Formatting & History Management:** Because MedGemma’s official documentation notes it has not been evaluated or optimized for multi-turn applications, the application layer shall manage conversation history via structured turn re-formatting (injecting recent user/assistant turns into the instruction prompt) to sustain coherent multi-turn context (up to 2,048–4,096 tokens).
* **FR-CHAT-02 (P0): Streaming Output:** The UI shall display model response tokens progressively in real time as they are generated by the local inference engine.
* **FR-CHAT-03 (P0): Session Lifecycle Management:** The user shall be able to create new conversations, rename titles automatically or manually, archive conversations, and delete individual or all chat histories.
* **FR-CHAT-04 (P0): Context Grounding Badge:** Every response generated with document evidence must clearly display an interactive "Grounded in Vault" badge linking to source citations.
* **FR-CHAT-05 (P0): Generation Control & Cancellation:** The user shall have the ability to abort an active generation mid-stream; system must release KV cache and inference thread immediately upon cancellation.
* **FR-CHAT-06 (P1): Ephemeral Clinical Disclosure:** Collapsible disclosure widget rendering grounding summaries and confidence indicators.

### 3.2 Medical Vault & Document Processing (FR-VAULT)
* **FR-VAULT-01 (P0): Multi-Format Ingestion:** Ingest digital PDF files and standard image formats (JPEG, PNG, HEIC) via Android System File Picker.
* **FR-VAULT-02 (P0): Native Document Preservation:** Original binary documents must be copied into encrypted internal app storage (`context.filesDir/vault/documents/`) with immutable UUIDs.
* **FR-VAULT-03 (P0): Local Text Extraction:** For digital PDFs, text and structural coordinates must be extracted using on-device PDF parsing libraries.
* **FR-VAULT-04 (P0): On-Device OCR:** For scanned documents and images, text shall be extracted locally using on-device OCR (ML Kit Text Recognition or offline Tesseract) supporting Latin and Devanagari scripts.
* **FR-VAULT-05 (P0): Document Metadata Annotation:** Each document must store: Document Title, Report Date (clinical date of test), Ingestion Date, Laboratory/Clinic Name, Document Type, and Extraction Status.
* **FR-VAULT-06 (P0): User Correction of Extracted Metadata:** The user must be able to edit and confirm document date, title, and provider name if OCR or extraction is imperfect.
* **FR-VAULT-07 (P0): Atomic Document Deletion:** Deleting a document must atomically purge: physical file, extracted text, chunk embeddings from vector store, and linked unconfirmed extraction tables.

### 3.3 Medical Report Simplifier & Biomarker Extraction (FR-SIMP)
* **FR-SIMP-01 (P0): Deterministic Biomarker Parsing:** The system shall extract laboratory test records into structured relational fields: `Test Name`, `Observed Value (Numeric/String)`, `Standard Unit`, `Reference Range Low`, `Reference Range High`, and `Abnormal Flag (High, Low, Normal, Critical)`.
* **FR-SIMP-02 (P0): Deterministic Flagging Logic:** Out-of-range determinations must be computed mathematically by application logic based on the printed reference range, not left to LLM statistical conjecture. MedGemma explains verified data rather than discovering raw numbers.
* **FR-SIMP-03 (P0): Grounded Plain-Language Explanations:** MedGemma shall generate simple explanations explaining what each flagged biomarker represents in bodily function (e.g., "Creatinine reflects how well your kidneys filter waste").
* **FR-SIMP-04 (P0): Extraction Uncertainty Highlighting:** Any measurement where the unit or reference range could not be resolved with high confidence must be flagged with an "Unverified / Review Needed" indicator.
* **FR-SIMP-05 (P0): Direct Source Jump:** Tapping on any extracted measurement card in the UI must immediately open the original document viewer scrolled to the exact page and highlighted coordinate.

### 3.4 Longitudinal Medical History (FR-HIST)
* **FR-HIST-01 (P0): Four-Tier Provenance Tracking:** Every item in the personal health record must be tagged with its provenance level:
  1. `USER_DECLARED` (Entered manually by user).
  2. `DOCUMENT_EXTRACTED_UNVERIFIED` (Parsed by OCR/AI, awaiting review).
  3. `DOCUMENT_EXTRACTED_CONFIRMED` (Reviewed and accepted by user).
  4. `AI_INFERRED` (Synthesized insight; strictly informational).
* **FR-HIST-02 (P0): Structured Health Profile:** Relational tables must store: Confirmed Conditions, Allergies, Active & Past Medications, and Longitudinal Biomarker Series.
* **FR-HIST-03 (P0): Cross-Report Trend Analytics:** When at least two reports contain compatible biomarkers (e.g., Fasting Glucose on Jan 2025 and Aug 2025), the system shall render a chronological comparison table and directional indicator (Improved / Elevated / Stable).

### 3.5 Genuine Local RAG (FR-RAG)
* **FR-RAG-01 (P0): Semantic Chunking:** Extracted report text must be segmented using layout-aware chunking (preserving test name, result, and reference range in the same chunk) with a target size of 256–512 tokens and 50-token overlap.
* **FR-RAG-02 (P0): Dedicated On-Device Vector Embeddings:** Chunks must be embedded using a separate local embedding model (**EmbeddingGemma 300M**, 768 dimensions) executed via LiteRT.
* **FR-RAG-03 (P0): Local Vector Index:** Embeddings must be persisted locally with Cosine Similarity search support, targeting sub-30ms retrieval over up to 1,000 chunks.
* **FR-RAG-04 (P0): Hybrid Retrieval (Vector + Relational SQL):** Query execution must route numerical and temporal questions (e.g., "What was my highest platelet count?") to SQL aggregates, and conceptual questions ("Why is my bilirubin high?") to vector search.
* **FR-RAG-05 (P0): Explicit Citation Rendering:** Generated answers from MedGemma must include inline numerical footnotes `[1]`, `[2]` linking to a bottom drawer showing: Document Name, Report Date, Page Number, and Exact Text Snippet.
* **FR-RAG-06 (P0): Negative Retrieval Handling:** When no relevant chunks or records exceed the similarity confidence threshold (cosine distance > 0.45), the system must explicitly declare: *"I could not find information regarding this test in your saved medical records."*

### 3.6 Healthcare Safety & Emergency Escalation (FR-SAFE)
* **FR-SAFE-01 (P0): Deterministic Red-Line Emergency Triage:** A deterministic keyword and regex triage classifier must intercept user queries *before* LLM execution. Red-line conditions (severe chest pain, signs of stroke [FAST], respiratory distress, severe allergic reactions, heavy bleeding) must immediately trigger an Emergency Modal.
* **FR-SAFE-02 (P0): Emergency Action Card (India 112 Standard):** The emergency UI must present a single-tap button to launch the native Android dialer pre-populated with `112` (National Emergency Response System of India) and present clear, immediate first-aid instructions.
* **FR-SAFE-03 (P0): Mandatory Non-Diagnostic Disclaimers:** All generative responses must include persistent non-diagnostic indicators clarifying that SwasthAI provides educational interpretation, not physician diagnoses.
* **FR-SAFE-04 (P0): Hallucination Guardrail (Fact Verification):** Generated text must be cross-checked against retrieved biomarker values before display. If the LLM generates a numerical value that does not match any retrieved source chunk, the UI must flag the discrepancy.

### 3.7 Multilingual Support (FR-LANG)
* **FR-LANG-01 (P1): Hindi Language Support:** The application UI and plain-language medical explanations must support full Hindi rendering.
* **FR-LANG-02 (P1): Medical Entity Preservation:** When generating Hindi explanations, clinical entities, drug brand names (e.g., *Metformin*, *Thyronorm*), and exact lab values/units must remain in Latin script or bracketed English transliteration to prevent confusion.
* **FR-LANG-03 (P2): Regional Language Extensibility (Tamil/Telugu):** Architecture must decouple localization strings and prompt templates to allow plug-and-play regional Indian language support.

### 3.8 Bounded Agentic Workflows & Preventive Care (FR-AGENT)
* **FR-AGENT-01 (P1): Explicit Tool Schema:** Tool invocation by MedGemma must use strict JSON schema validation. Permitted tools:
  - `search_medical_vault(query: String, date_range: String)`
  - `get_biomarker_history(biomarker_name: String)`
  - `create_medication_reminder(drug_name: String, time: String, dosage: String)`
  - `generate_doctor_consultation_summary(condition_filter: List<String>)`
* **FR-AGENT-02 (P1): Human-in-the-Loop Confirmation:** No tool that mutates state (e.g., creating a medication reminder or saving a health fact) may execute without explicit user approval via a confirmation dialog.
* **FR-AGENT-03 (P1): Local Notification Scheduling:** Reminders must be scheduled using Android `WorkManager` and `AlarmManager` without external push notification services.

## 4. Non-Functional Requirements (NFR) — Proposed Engineering Targets

> [!NOTE]
> All quantitative metrics below represent **proposed engineering targets to be experimentally validated** on the physical Samsung Galaxy S25 during Phase 0 and Phase 7 testing, NOT pre-achieved facts.

### 4.1 Performance & Latency Targets (NFR-PERF)
* **NFR-PERF-01: Time to First Token (TTFT):** Proposed target for MedGemma 1.5 4B IT with 512 context tokens is **< 1,200 ms** under GPU/NPU acceleration, to be benchmarked on device.
* **NFR-PERF-02: Generation Throughput:** Proposed generation target is **>= 12–15 tokens per second** on Snapdragon 8 Elite under standard room-temperature conditions.
* **NFR-PERF-03: Retrieval Latency:** Proposed target for end-to-end RAG retrieval (query embedding + top-5 vector search + SQL lookup) is **< 60 ms**.
* **NFR-PERF-04: Document Ingestion Throughput:** Proposed target for 2-page digital PDF report parsing, chunking, and embedding is **< 4.0 seconds**.

### 4.2 Memory & Storage Targets (NFR-MEM)
* **NFR-MEM-01: Peak Resident Memory Target:** Total application resident memory footprint under active MedGemma generation must target **<= 3.5 GB RSS**, leaving headroom for Android 15 system processes. Must be empirically verified via `dumpsys meminfo`.
* **NFR-MEM-02: Strict Sequential Execution:** The embedding model (EmbeddingGemma 300M) and the generative model (MedGemma 1.5 4B IT) are scheduled sequentially during document ingestion to minimize concurrent peak memory.
* **NFR-MEM-03: On-Device Storage Quota:** Total storage consumption for all application code, runtimes, and model weight files must not exceed **5.0 GB**.

### 4.3 Privacy & Data Security (NFR-SEC)
* **NFR-SEC-01: Air-Gap Enforcement:** The application must operate without requiring `android.permission.INTERNET`. Zero diagnostic data, vectors, or chat transcripts may be transmitted over any network socket.
* **NFR-SEC-02: Encryption at Rest:** All relational databases (Room/SQLite), vector index files, and cached PDF/image documents must be encrypted using AES-256-GCM with keys managed by the hardware-backed **Android Keystore System** (StrongBox / TEE).
* **NFR-SEC-03: Screen Capture Protection:** Medical Vault screens must enforce `FLAG_SECURE` where designated by user preference to prevent unauthorized capture.

### 4.4 Reliability & Robustness (NFR-REL)
* **NFR-REL-01: Low Memory Killer (LMK) Resilience:** If the application process is terminated in the background, active chat state and unsaved document drafts must be recovered via Room transaction journals upon restart.
* **NFR-REL-02: Thermal Monitoring:** The inference engine must monitor device thermal status (`PowerManager.getThermalHeadroom()`) and throttle generation parameters if device thermal status approaches `THERMAL_STATUS_SEVERE`.
